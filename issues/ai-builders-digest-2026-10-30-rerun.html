Latent Space 在 AI Engineer New York 2026 现场对话 Arca 的 AI 平台团队负责人 Aman Singh——这家 AI 原生财富管理公司最近融资 6400 万美元。一句话论点：「我们不是 SaaS 公司，我们就是公司本身。agent 提示人的次数比人提示 agent 还多——主动式 24×7 服务。」核心线索：AI 取代的是「围绕顾问的工作」而非顾问本人——客户完全不直接接触 AI，只是体验到以前不可能的服务水准；模型按任务复杂度分档（税务分析用最重的 Opus/Sonnet/GPT 档、后台活动用低档），且对顾问完全透明——内部基准高于外部基准（Luna 外部跑分很好、实际又慢又贵；Claude 主力、模型无关是原则、harness 自建）；十天税单工作流——分析全归 agent、但动钱/变现/直接联系客户强制 human-in-the-loop；长程任务靠记忆系统（每客户的状态、归属、下一步）+「做梦」反思过程延续，新信号唤醒的 agent 秒速上手；安全——确定性限制优先、每次写库都有 LLM 校验、边缘检测 prompt 注入、出站数据过 PII 检查 + 小模型共识防外泄、默认可审计（agent 与人的每个动作都产变更日志）；为什么不用托管 agent——「拥有你的记忆与运营知识就是拥有你的智能」；沙箱——agent 不在沙箱里、把计算卸载进去：生成的代码被翻译成严格格式后丢弃原码，财务计划 PDF 产出即过确定性检查（禁裸账号）+ 快速模型（小模型或 JEV）查合规（禁承诺收益）——「AI 做合规比人强，因为它找最小违规时不知疲倦」；决策模型——前沿模型会自信地用错年份税率档，决策模型在金融建议前拦截、推向已验证事实库；不做自主交易——agent 提议、专家执行；反馈即评估——每次编辑取消带 why、与 trace 配对、每晚 meta agent 复盘建议 harness 改动（人类工程师仍把关 prompt，因为放任 agent 会把每个小修变成整个 prompt 重写）；公司知识库是产品一等公民标签页、专家策展、agent 引用；客户案例——agent 读准客户的报表，发现隐藏费用、且原顾问根本不是受托人；截止日与 RMD 提醒是 agent 的默认行为——人类在规模上做不到。完整译文见下。

【冷开场：我们不是 SaaS 公司，我们就是公司本身】

「我们其实不是一家 SaaS 公司。我们就是这家公司本身。在我们的系统里，agent 提示人的次数比人提示 agent 还多——这是一种主动式的服务，为客户 24×7 不间断地运行。」

（现场）这里是 2026 年 AI Engineer New York 大会，我和 Arca 的 Aman Singh 坐在一起。Arca 最近为这家 AI 原生的财富管理公司融资 6400 万美元。

【Arca 是什么：AI 原生财富管理】

问：Aman，先介绍你在 Arca 的角色、你们提供的金融服务，以及怎么用 AI agent 来跑这些业务？

Aman：谢谢邀请。我在 Arca 带领 AI 平台团队——我们在造底层的 harness 与能力，最终目标是「用 AI 来经营这家公司」。

我们给客户提供的是很宽谱系的金融服务：财务咨询与财务规划、税务规划、保险、以及财富增长后的遗产规划。客户画像也很广：比如刚卖掉公司的人——各种合作方与复杂性一团乱麻，我们帮你理清；也有大型科技企业的高管，在认真规划提前退休；也有正想买第一套房的小家庭。

问：目前的客户，你们需要跟他们解释「你们在用 agent」这件事吗？

Aman：AI 在 Arca 的角色不是取代顾问，而是取代「围绕顾问的所有工作」。我们的客户并不直接接触 AI——他们体验到的只是一种这个行业以前从未有过的服务水平，通过人类顾问的共情与关怀交付。我们为每个客户背后造了一台不停运转的机器：市场在发生什么、这对 Richard（客户）意味着什么？你的生活里还有什么事在发生——哪些「生活的纹理」会影响你的财务？用 AI 干完所有后台工作之后，我们能主动得多、响应快得多、客户服务好得多。

【模型选型：内部基准说了算，模型无关是原则】

问：技术上，你们用哪些模型驱动 agent？怎么决定哪个模型干哪件事？

Aman：现在用的是前沿实验室的前沿模型，主要是 Anthropic 和 OpenAI。Claude 是我们的主力模型——这些年来我们迭代过好几代：最早用 Gemini，后来 OpenAI，再后来 Anthropic。指引所有决策的是我们的内部基准——针对我们 harness 在经营业务时必须表达的各种能力建的基准。

举个例子：最近 Luna 这个模型，尽管外部基准把它夸上天，在我们这儿实际表现远不及预期——太慢了，而且成本很高。所以是内部基准在指导模型决策。原则上我们保持模型无关：不对某一家供应商或某家的 harness 形成依赖，把这个可选择性留在自己手里。

问：你刚提到 harness——你们按模型配不同 harness？

Aman：不。我们有自己的 harness，内部自建、模型无关。

问：那当顾问做税务报告之类的事时，harness 怎么决定用哪个模型？自动的吗？

Aman：是的。我们按任务复杂度分了几档模型。像「协助税务规划/税务分析」这种任务会用最重的一档——这一档内部有一定灵活性，可以是 Opus 档、Sonnet 档或重量级 GPT。而 agent 们在后台做的大量背景活动，就按复杂度用更低档的模型。模型怎么配任务，是我们内部决定的。

问：是财务顾问自己在产品里选模型吗？

Aman：不是。他们根本感知不到这一层——我们把它完全抽象掉了。他们就像平常一样用产品，这些决策由我们在内部完成。

【税单案例：十天的长程任务怎么分工】

问：你今天大会演讲里讲了税单的例子。能不能带我们走一遍「调整客户投资组合」的完整流程——从发现需要再平衡，到执行交易——哪部分是 agent 做、哪部分是人做？

Aman：就像演讲里说的，这类事情会横跨十天。最终为交付结果负责的是 agent，但有些部分它们做、有些不做。

这个例子里，客户发邮件来说有这么一笔税单。其中有一块分析是：客户的钱现在配置在哪、liquidate 哪些、怎么 liquidate 最优，才能凑出这十万美元？这种分析任务最适合 agent——它们就干这个。

问：但它们有权限限制对吧？不能自己执行交易？

Aman：对。分析环节全自动，但它们不能自动执行任何资金移动或资产变现。我们与托管方有很深的集成、有相应 API 能做这件事——但对「会动钱、会变现资产、甚至直接联系终端客户」的事，我们有严格的 human-in-the-loop 护栏，因为我们要求的服务与质量水准摆在那里。所有内部分析由 agent 完成；需要执行交易时，它们会把对的人拉进来，把一份可供审阅与调整的方案交给那个人。

问：这些流程动辄十天，比现在大多数 agent 任务都长。当 agent 隔了几天再恢复任务时，怎么检查计划仍然符合客户需要？

Aman：这个很有意思。我们有大量信号。比如一个邮件 thread 在持续收到回复、有讨论在发生——任何新的回复都会进入那个正在跟读、正在响应这个 thread 的同一个 agent。但一个全新的信号——比如中间来了通电话——是没附着在任何进行中流程上的：会有一个全新的 agent 被唤醒，去搞明白这是什么。

它们理解「现在正在发生什么」靠的是我们的内部记忆系统：对每个客户——现在在发生什么？我们在服务什么事项？谁拥有什么？到目前为止发生过什么？接下来几天要立刻发生什么？长期在追踪什么？每个行动由谁负责？——全部由我们的记忆系统追踪，agent 们向它贡献。

还有一个类似「做梦」的过程：反思与 Richard 有关的世界的状态，并更新这些记忆系统，让长程任务得以延续。所以那个接到新信号的 agent 能快速 ramp up：哦，我们正在处理一笔大税单——我的信号和它相关——让我为这个世界的状态添砖加瓦。

【安全护栏：确定性优先，围堵在能力边缘】

问：安全方面呢？怎么确保路上不丢钱？

Aman：我们所有的安全限制都是完全确定性的——把决策从 agent 手里拿走。比如某些工具允许 agent 直接执行（简单的记账类工具）；而每次调用写数据的工具，我们都有一个基于 LLM 的校验在跑——用快速的 LLM 调用分析每一次对数据库的写入。这是又一层验证。

另外我们摄入大量外部信息：进来的邮件、文档、打来的电话——这些都是 prompt injection（提示注入）的靶子。所以我们在边缘跑检测，识别某些注入类型的存在。

还有任何数据要离开系统的时刻——最典型是网页搜索，但给 Richard 发日历邀请也算——我们既有对已知 PII 的确定性检查，也有一组小模型做共识判断，确保没有数据外泄的企图。我们的原则是：把护栏围堵在「能力的边缘」，而不是更早的地方。

问：金融业有监管要求吗？

Aman：这个行业关心结果，而合规关心可审计性。我们的系统是「默认可审计」：agent 的每一个动作都会产生变更日志——改了什么、谁改的、从系统哪个部分改的、什么时候。顺带说，这不只适用于 agent，也适用于人类：你在 UI 里改了任何影响客户的东西，我们都会记录。这既给了我们默认的可审计性，也反哺了 agentic 能力——追踪 UI 变更的同一套东西，也可以用来告诉 agent「刚刚发生了这件事」。可审计性既是合规与监管的故事，也是我们 agentic 循环的一部分。

【「Agent 提示人」与为什么不托管给实验室】

问：你演讲里有句好话：「Agent 提示人的次数比人提示 agent 还多。」agent 怎么决定拉谁进来、给那个人多少上下文？

Aman：这和我们这个行业里人与人的协作方式很像：一个十天的流程、多个参与者，第七步的那个人此刻未必需要知道这件事——他在正确的时机被拉进来。我们的 agent 依靠长记忆的持久化 + 对世界状态的每日反思，判断当下世界到哪一步了、什么信号意味着该把谁拉进来。

而这一切的前提，是我们把「这个行业怎么运转」、以及「Arca 希望它怎么运转、我们的工作原则是什么」做了操作化。这也是我们不是 SaaS 公司的又一个优势：我们能标准化工作发生的方式，让 agent 以标准方式参与其中。

问：今天早上 Anthropic 做了他们托管 agent 基础设施的 workshop，连编排都越来越自动了。你们会用这类东西吗？毕竟人未必总在环里，有风险。

Aman：我们对 Anthropic 和 OpenAI 这些实验室的模型非常看好——但对依赖「托管 agent 产品」这件事不那么看好。因为托管 agent 的核心之一是模型怎么持久化与贡献记忆、以及它们要成功所需的全部运营知识。把这部分交给别人，等于把「你的智能」交了出去——而拥有自己的智能，才有能力影响业务。交出去，你就失去了构建「高度独特、深度贴合你业务、真正能影响业务」的东西所需的控制力。

问：Anthropic 最近也发布了金融服务方案、在跟一堆金融机构合作。他们跟你做的是竞争吗？

Aman：Anthropic 进入我们这个行业，对整个行业是很大的验证。但我的看法是：「一家用着 AI 工具的服务公司」和「一家为 AI 原生而生的公司」非常不同。前者要求用户去提示 agent 才产出工作；而在 Arca，agent 提示人的次数比人提示 agent 还多——是主动式、24×7 的服务，以我们期望的服务水准、以最标准的方式经营着业务。如果你是「有 AI 工具的公司」，看起来会完全不一样。

【沙箱、验证器与决策模型】

问：安全再说深一点：什么跑在沙箱里？怎么在任何人行动之前验证一份财务计划的变更？

Aman：沙箱是我们 harness 的一个组件。我们的 agent 并不在沙箱里面——它把计算卸载到沙箱。我们做了系统让沙箱里的代码能安全地访问我们的数据：agent 写的代码会被翻译成我们期望的严格格式、把原代码扔掉、在触达后端之前对格式施加护栏。这样 agent 可以用代码查询我们的数据——聚合、清洗、随心所欲地加工——来产出比如一份财务计划；同一个沙箱里它还产出漂亮的交付物：一份 PDF——「这是你的财务计划、这是我们打算如何在财务上安排你的人生」。产出的那一刻，我们就跑验证器：有确定性的——「你是不是把裸账号放进去了？不许这样」；也有快速模型（小模型或 JEV）——检查会不会让这份产物不合规的东西，比如你真的不应该在里面承诺收益。AI 做合规其实比人做得更好——它在找出最小的一处不合规表述上是不知疲倦的。我们会继续在这里投入、继续在能力边缘围堵。

问：你提到 JEV——你们开始用决策模型了。除了 Jev 还在看什么？

Aman：我们注意到：当模型处理金融数据、回答需要金融知识的问题时，它们对自己掌握的知识非常自信。一个小例子：模型会开开心心地用 2025 年的税率档来做分析、然后说「好了就这样」——这显然是错的。所以我们在 harness 里用决策模型的方式之一就是：当模型即将做出金融建议、或任何需要金融严谨性的动作时——检测它，并把它推向我们「今天为真的已验证事实」知识库、和/或让它做网页搜索。这也是「拥有自己的 harness」的又一个好处：你能让你的模型在要紧的地方保持准确。

问：交易失败时，恢复环节有决策模型参与吗？

Aman：现在没有，不是我们在探索的用例。而且我们目前不做 agent 自主交易：agent 提议交易，是否正确、是否执行，完全由我们的专家判断和执行。

【反馈即评估：每晚的 meta agent 例会】

问：你的幻灯片说「每次员工编辑或取消都带着一个 why、并变成一条 eval」。这个反馈怎么变成可度量的改进？

Aman：这也是「我们自己就是业务、不是 SaaS 公司」的优势：我们有能力要求他们给反馈。反馈回流改进的方式如你所料：所有反馈被管道送进一个数据存储，和产出它的 agent 的 trace 配对。每天晚上，我们收集真实世界里 agent 的 trace，在其上跑一个 meta agent——它建议对 harness 的修改：哪些工具有误导性、哪些地方出错了、知识库里缺什么知识——把这些浮出来给我们，然后我们改进。

今天，在真正上线一条 prompt 修改之前，我们仍然保留一位人类工程师在环里。因为把 agent 放任自流，它们会把 prompt 改得非常难看——每个小修小补都变成重写整个 prompt，它们没法保持元层面、把修法泛化成一条可泛化的规则。

问：你也讲了把「公司怎么运转的知识」变成 agent 上下文——很多 forward deployed 工程师都在做这件事。你们技术上长什么样、怎么保持最新？

Aman：我们有一个以文件形式呈现的知识库。保持更新的方式：交给我们的专家来策展和更新——它是产品里的一等公民功能：左边有个叫 Knowledge 的标签页，装着我们 agent 在用的全部运营上下文。agent 工作时会引用知识，于是形成了循环：发现知识有误，在我们的 trace 分析里浮出来；因为知识库就是产品本身的一部分，人们可以直接进去改。

【客户案例：抓出隐藏费用与受托义务缺失】

问：最后，能不能举一个客户因 agent 架构获得可度量改善的例子？

Aman：讲个最近的。这个人当时还不是客户、正处在签约边缘——我们拿到了他的全部文件、报表、现有投资。他已经在跟一位顾问合作，见面时说：「我有顾问了，收我 1500 美元服务费，但响应很不及时，所以来跟你们聊聊。」

我们的 agent 读完了所有文件并分析：他声明的目标是什么、这位现任顾问的报表是什么、收了他多少钱——然后发现：这位顾问在收他一些他根本不知道的费用；并让他意识到：这个人甚至都不是 fiduciary（受托人）——没有法律义务按他的利益行事。这就是我们的 agent 在分析财务图景时带来的那种注意力细节——没有它们不可能做到。

还有一堆主动性的例子：某人有截止日期要到了、有人有错过 RMD（最低分配额）的风险——这类事让人类在规模上全部盯住极难，但在 Arca，这是 agent 的默认行为。

Aman：谢谢邀请。
